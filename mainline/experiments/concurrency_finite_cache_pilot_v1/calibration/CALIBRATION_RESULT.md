## 校准问题的回答

1. **是否持续竞争（而非仅 setup 驱逐）**：是。0.25 MiB 档在整程产生 **18334 次驱逐**，
   且 **32/32 节点**都出现驱逐（`competing_nodes=32`）；unlimited 为 0（符合预期，不作失败）。
2. **预热影响**：
   - unlimited：warmup p95 = **339.74 ms** → measurement p95 = **154.87 ms**（−54%），冷启动瞬态明显；
   - 0.25 MiB LRU：warmup p95 = **389.14 ms** → measurement p95 = **402.48 ms**（+3.4%），稳态很快建立。
   因此 25% 预热排除是必要的（尤其对 unlimited 基线），且不会把有限档的稳态削掉。
3. **测量段样本是否足够描述延迟分位**：测量段 **3072** 个完成请求，远超 1000 的门槛；
   `latency_sample_note` 未触发“样本不足”。
4. **请求积压是否持续增长**：否。最后到达后**排空 1.29 s**（0.25 MiB）与 **0.03 s**（unlimited），
   窗口吞吐接近 offered rate，无持续积压。
5. **全 trace + 监控的开销**：单 run wall ≈107 s（含 32 节点启停约 60–70 s）；磁盘与验收耗时在预算内。

## 冻结（校准后）

- **预热 = 计划到达窗口前 25%**（1024 个测量请求）。
- **测量 = 后 75%**（3072 个测量请求），以**计划到达时间**切分。
- **长度 = 冻结的完整 schedule**（32 setup + 4096 measurement，Poisson 128 /s），**不延长**。
- 冷启动轨迹（warmup 段）单独保留、不与稳态测量段混合；所有指标的分母均为测量窗口。
